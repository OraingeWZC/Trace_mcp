## 1. 五板块评测范式对照（与项目全景文档同步）

### 1.1 算法栈与训练负担

| 板块 | AD | RCA | CLS | 训练量 | 评测脚本 |
|---|---|---|---|---|---|
| **log_tools** | DeepLog / LogBERT（每 service 一份权重） | 跨 service AD 聚合排序 | TF-IDF + LR / LogBERT 分类器 | 中 | `evaluate_log_tools.py` |
| **metric_tools** | BOCPD（无训练） | RobustScorer / N-Sigma（无训练） | LR on RCA-ranks（轻训） | 几乎无 | `evaluate_metric_tools.py` |
| **metric_log_tools** | 复用 metric_tools | 复用 metric_tools | 复用 metric_tools | 无 | `evaluate_fused_tools.py` |
| **trace_tools**（指标 3.2） | TrUST GVAE 双自编码器（**linyu**） | TrUST 柔性聚合 Top-K（**linyu**） | trace_sv_diag 多头分类（**wzc**）| 重 | 团队自有方案，无顶层入口 |
| **trace_topo_tools**（指标 3.4） | TraTopoRca GVAE+三通道（**wzc**） | TraTopoRca 服务级+主机级对齐（**wzc**） | trace_svnd_diag 含 Host Graph（**wzc**） | 最重 | 团队自有方案，无顶层入口 |
| **OpsAug/ART**（指标 3.5） | 五模态预训练 SSL | RCL | FT (failure triage) | 最重 | `evaluate_opsaug_*.py` |

### 1.2 train/test CSV 在各板块的真实角色

| 板块 | train CSV 角色 | test CSV 角色 |
|---|---|---|
| log_tools | 训 fault-type LR 分类器（`train_fault_type_classifier.py`） | 直接喂 `evaluate_log_tools.py` 逐 case 评测 |
| metric_tools | 跑 pipeline → 训 6 类 LR | 直接喂 `evaluate_metric_tools.py` |
| metric_log_tools | 同 metric_tools | 直接喂 `evaluate_fused_tools.py` |
| **trace_tools / trace_topo_tools 现状** | **未消费**——shell 写死自定义时段 + 老版 GT | **未消费**——内部 7:1:2 切代替 |

### 1.3 其他三板块的评测脚本统一工作模式

```
读 GT CSV 每一行 (start_time, end_time, instance_type, root_cause_entities, fault_type, observed_signals)
  → 按 observed_signals 过滤（log 板块要 logs，metric 板块要 metrics，融合板块要两者皆含）
  → 拉对应窗口 / 服务的数据
  → 跑 AD / CLS / RCA pipeline
  → 与 GT 字段比对，逐 case 算命中
  → 汇总 AD-F1 / CLS-macroF1 / LOC-Top@K
```

每条 case 是独立的"窗口推理 + GT 比对"，没有跨 case 的 train/test split 概念。

## 2. trace 板块当前范式（已认证版本）

### 2.1 算法栈

- **trace_tools/TrUST**（**linyu**）：GVAE 双自编码器（结构子网络 + 时序子网络），三大评分优化（Bernoulli-Categorical Scaling / Gaussian Std Constraint / Node Count Normalization）+ 柔性最大值归一化聚合
- **trace_tools/trace_sv_diag**（**wzc**）：去 Host Graph 的 Scheme B 简化版多头分类
- **trace_topo_tools/TraTopoRca**（**wzc**）：Call-GAT + Host-GCN + Tree-LSTM 三通道并行编码 + GVAE 重构残差 → AD/RCA
- **trace_topo_tools/trace_svnd_diag**（**wzc**）：API/Status/Node Embedding + 双 GCN + Host GCN/GAT + TreeLSTM Readout + 三头分类（det/c3/type）

### 2.2 当前数据流

`scripts/trace_topo_tool.sh` 实际调用：

```bash
# 正常数据：写死的 90 分钟时间窗
python -m dataprocess.scripts.data_fetch \
  --start-time "2026-03-05 05:00:00" \
  --end-time   "2026-03-05 06:30:00" \
  --max-traces 100000 ...

# 故障数据：用单个 GT 文件
python -m dataprocess.scripts.fault_data_fetch \
  --gt-csv dataprocess/dataset/rca_gt_0305_0317.csv ...
```

→ 两个 benchmark CSV 都没出现，老版 `rca_gt_0305_0317.csv` 时段也不对齐。

### 2.3 内部 split 的现状

- `TraTopoRca/dataprocess.py::split_and_convert_csv`：按 **TraceID** 7:1:2 切分。
- `trace_svnd_diag/make_tc_svnd.py::split_by_problem_id`：按 `problem_id` 内部时间顺序 7:1:2 切——**每个 problem 同时进入三个 split**。
- `trace_tools/trace_sv_diag/tc_make.py` 同结构、同方式。

**这套方案在 CCF AIOps 数据集 + 阿里云原生测试环境上跑出了赛西认证的指标**，所以"问题"二字加引号——它达到了项目要求，只是与其他板块的"逐 case GT 对比"范式不同。

## 3. 假如要对齐成项目级范式（可选）

### 3.1 目标范式

```
benchmark-groundtruth-train-0305-0315.csv  ──┐
                                              │   解析所有行 → 推导待拉时间区间并集
                                              │   按 (start_time, end_time, instance_type,
                                              │      target_instances) 逐行拉故障 trace + metric
                                              │   同时段补拉一批正常 trace 作为负样本
                                              ▼
                                          训练数据（带 GT 标签）
                                              ↓
                                       端到端模型训练（保留 ckpt + stats + keep_types）
                                              ↓
benchmark-groundtruth-test-0316-0325.csv ──┐
                                              │   同样方式逐行拉数据
                                              ▼
                                          测试数据（带 GT 标签）
                                              ↓
                              逐 case 推理 → 与 GT 对照
                                              ↓
                       AD-F1 / CLS-macroF1 / LOC-Top@K
                              （对齐 metric_tools / log_tools 评测口径）
```

关键区别：**两个 CSV 是天然的 train/test split，模型内部不再做 7:1:2**。需要 val 时，从 train CSV 时段里再留最后 1~2 天作为 hold-out（按时间，不按 problem_id 内部切）。

### 3.2 收益与代价

| 收益 | 代价 |
|---|---|
| 与 metric/log 板块的数字横向可比 | 数据获取脚本要重写（接受 GT CSV） |
| 接入 OpsAug 五模态融合时数据契约更清晰 | 内部 split 逻辑要重构 |
| 测试集真实未见，泛化能力评估更严格 | 短期内 F1 数字可能下降（但更可信） |
| 可以在 `results/` 出具与其他 baseline 同格式的报告 | 工程量约 1~2 周 |

### 3.3 触发条件

只有在以下情况之一发生时才推荐做这个改造：
- 课题验收要求统一指标输出口径
- OpsAug 团队需要拿你的 ckpt 接入五模态融合（指标 3.5）
- 你想发表论文做横向对比实验

否则维持现状即可。

## 5. 不要做的事情

- 不要在 train / test 共用一份 `stats`（均值方差），各自拟合各自的。**例外**：normalize 的 reference 必须用 train 拟合后保存进 ckpt，test 推理时加载使用——避免数据泄漏。当前 `train_tc_svnd.py` 已经这样做（`ds_fit.stats` 来自 train），改造后保持。
- 不要保留"按 problem_id 内部 7:1:2"这种隐性泄漏。
- 不要再为了"每个细类在 train/val/test 都出现"而做事件内部切分——细类频次不均衡是测试集真实情况，正是要评测的对象。
- 不要继续无视 GT CSV 的 `observed_signals` 字段——其他板块都按它过滤 case。

## 6. 对照实验资源

### 6.1 项目内：ART/OpsAug 家族（轨迹+拓扑+多模态融合）

只有 ART/OpsAug 家族（`ART_baseline/` / `OpsAug-main/` / `opsaug_tools_v2/`）真正消费 trace 模态，**是指标 3.4（轨迹+拓扑融合）唯一同维度对手**。其他融合 baseline（DiagFusion / DejaVu / MULAN / Nezha / Hades / AnoFusion）默认关 trace。

对照路径：
- 在同一份 `benchmark-groundtruth-test-0316-0325.csv` 上跑：
  - 你的 trace_topo_tools（改造完成后）
  - `evaluate_opsaug_ad.py --modalities metric,log,trace`
  - `evaluate_opsaug_diag.py --tasks ft rcl --modalities metric,log,trace`
- 输出按 `results/anofusion_runs_summary.md` / `art_runs_summary.md` 等已有报告的格式，落盘到 `results/trace_topo_runs_summary.md`。

### 6.2 师门内部：TADBench（轨迹单模态 baseline 库）

`/Users/wzc/Project/bk/TADBench/` 是裴丹组合作产出的 trace AD benchmark（IEEE TSC 2025），**论文作者之一是本课题 PI 裴丹**——所以 TADBench 实质是师门内部对照基线，不是第三方。

- **指标 3.2 的师门内部对照**：TraceVAE / PUTraceAD / TraceAnomaly / CRISP / TraceCRL / Multimodal-LSTM / GTrace 共 7 个。
- **指标 3.4 的消融叙事**：所有 TADBench baseline 都是 trace-only，可用于"关 Host 通道的 TraTopoRca vs 纯 trace baseline"差距对比，证明拓扑+主机指标的增量贡献。
- **公开数据集补充**：AIOps2020（74MB，优先）/ TrainTicket / GAIA / AIOps2022 / AIOps2023（仓库缺，需 clone）。

**关键叙事**：TADBench 论文末尾的 *future direction* 明确呼吁集成 TraceVAE 三大评分优化 + GTrace 层次化图编码——linyu TrUST 同期独立开展的方法路线恰好沿这一方向（中期报告 3.3 节）。论文谱系：TraceVAE → GTrace → **TrUST**（同期独立工作，方向趋同）。

详细整合路径见 `TADBench整合方案.md`。
