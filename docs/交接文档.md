## 3. 数据契约（来自检测报告 + 实际代码）

### 3.1 轨迹 CSV（实际 16 列，CamelCase）

实际代码使用：
```
TraceID, SpanId, ParentID, ServiceName, NodeName, PodName, URL,
SpanKind, StartTimeMs, EndTimeMs, DurationMs, StatusCode, HttpStatusCode,
fault_type, fault_instance, problem_id
```

检测报告里写的是 snake_case 简化版（`trace_id, span_id, parent_span_id, service_name, duration, start_time, operation_name, status_code`）——实测时代码自带适配层处理了，但师弟接手时如果改 schema 要注意双向映射。

- 正常数据：`fault_type=normal`, `problem_id=normal_000`
- 故障数据：`fault_type` / `problem_id` 来自 GT CSV
- `instance_type ∈ {service, node, pod}`；`fault_data_fetch.py` 当前**显式跳过 pod**

```
fault_type, instance_id, timestamp,
node_cpu_usage_rate, node_memory_usage_rate, node_disk_usage_rate
```

实际代码扩展了更多列；默认 metric 类：cpu / mem / disk（在 `tracegnn/models/gtrace/config.py::HostState` 配置）。

## 4. 数据获取脚本（dataprocess）

### 4.1 trace_topo_tools/dataprocess/scripts/data_fetch.py

**职责**：在给定时间窗 `[start_time, end_time]` 内
1. 从 SLS tracing logstore 拉取全部 span（`LogClient + GetLogsRequest`）；
2. 提取 trace 中出现的所有 `k8s.node.name`，再从 CMS metricstore 拉对应 node 的 Prometheus metric（`.metric_set` SPL）；
3. 输出 16 列 trace CSV + metric CSV。

**关键过滤**：`_strict_trace_filter` 会丢弃
- `StatusCode > 1` 异常状态码
- 跨越拉取窗口边界的 trace
- span 数 < 2 的 trace

**调用示例**（来自 `scripts/trace_topo_tool.sh`）：
```bash
python -m dataprocess.scripts.data_fetch \
  --start-time "2026-03-05 05:00:00" \
  --end-time   "2026-03-05 06:30:00" \
  --max-traces 100000 \
  --output-dir dataprocess/data/normal --suffix _rca
```

### 4.2 trace_topo_tools/dataprocess/scripts/fault_data_fetch.py

按 GT CSV 逐行拉故障 trace + metric。
- 不做 `StatusCode` 过滤（与 normal 不同）
- 单组合最多保留 `max_traces_per_fault=5000`
- 输出：`Node_fault_trace.csv` / `Service_fault_trace.csv` / `Pod_fault_trace.csv`（pod 当前跳过）+ `Fault_nodemetric.csv`

### 4.3 trace_tools/dataprocess/scripts

与 trace_topo_tools 同名脚本基本一致，差异：
- 多一个 `csv-db.py`：把 `preprocess → merge → split → graph → SQLite` 整条流水线封装为 `whole_dataset()` / `test_data()` 两个入口（**TrUST 集成测试 YS02-007/008 用的就是这个**）。
- 默认路径写死在 `/mnt/sdb/zly/4.1/...`，迁移时需要修改。

## 5. TraTopoRca（指标 3.4 / 故障预警 + 根因定位 / wzc）

### 5.1 流水线

```
0_csv_merge.py        normal_metrics + fault_nodemetric → merged_all_infra.csv
1_make_tianchi.py     normal_traces + service/node_fault_trace + merged metric → raw/
2_process_tianchi.py  raw/ → dataset/rca/{train,val,test}/  (SQLite bytes + id_manager + vocab)
                     ↓ 同时调 dataprocess.py:precompute_host_states
mymodel_main.py       训练入口（--max_epochs / --batch_size / --report_dir）
mymodel_test.py       推理入口（--mode anomaly 或 --mode rca）
```

### 5.2 模型架构（中期报告 3.5 节）

```
分布式追踪数据 + 物理节点指标
        ↓
    [拓扑融合向量] [窗口上下文]
        ↓
┌──────────┬──────────┬──────────┐
│ Call-GAT │ Host-GCN │ Tree-LSTM│
│ 多层注意力 │ 双隐藏层  │ 子节点融合 │
│ 单层 RO   │ ReLU      │ root cell │
└──────────┴──────────┴──────────┘
        ↓
      MLP 融合 + GVAE 重构残差
        ↓
   ┌──────┬──────┬──────┐
   │ 预警 │ 定位 │ 诊断 │
   └──────┴──────┴──────┘
```

- **特征维度**：`num_features = 29`（13 emb + 16 node metric），写死在 `config.py::ExpConfig`
- **Host State**：4 维/指标（z0 / delta / max_z / mean_z），窗口 W=3 分钟，存进 `graph.data['precomputed_host_state']`
- **晚融合**：Trace 异常分 + Host 异常分加权 → 总分 → 阈值

### 5.3 切分逻辑（与赛西认证版本一致）

`dataprocess.py::split_and_convert_csv`：
- 默认 `train_ratio=0.7, val_ratio=0.1, test_ratio=0.2`
- 按 **TraceID** 切分

⚠️ 这是认证通过的实现。如果未来要对齐项目级"按时段切"范式，详见 `范式对比与改造思路.md` 第 4 节。

### 5.4 输出物

- `dataset/rca/{train,val,test}/data.db`（SQLite bytes 存储 trace 图）
- `dataset/rca/{train,val,test}/host_infra/*.npy`（预算 host_state 向量）
- `dataset/rca/{train,val,test}/vocab.json`（service/node/api 词表）
- `save/model/model.pth`（ckpt）
- `reports/eval_report_*.md`（赛西检测引用了这里的报告）

## 6. trace_svnd_diag（指标 3.4 / 故障诊断 / wzc）

### 6.1 流水线

```
make_tc_svnd.py    构造 train/val/test jsonl + vocab + meta
train_tc_svnd.py   联合训练三头（bin + c3 + type），早停 + ckpt 保存
test_tc_svnd.py   独立测试（从 ckpt 读 stats + keep_types）
```

### 6.2 数据集构造（`make_tc_svnd.py`）

输入：`--normal traces_rca.csv --service Service_fault_trace.csv --node Node_fault_trace.csv`

核心步骤：
1. `load_and_clean` + `drop_orphan_traces`（允许 ≤1 个悬浮根，丢断链 trace）
2. `per_trace_core`：每条 trace 抽取核心特征
3. `build_window_context_fast`：以 `dominant_node` 为 key，做 3 分钟滑窗上下文聚合
4. `host_state_vector_from_index`：从 metric 索引算 host_state 向量
5. `build_records`：组装 trace 图 + context + host_state + 三类标签
6. `split_by_problem_id`：按 problem_id 内部时间顺序 7:1:2 切

### 6.3 模型（`model_svnd.py::TraceClassifier`）

```
inputs: api_id, status_id, node_id, host_state, context
  ↓ Embedding (API / Status / Node)
  ↓ 双 GCN (trace 图)
  ↓ Host GCN/GAT (节点级 host state 图)
  ↓ TreeLSTM Readout (Child-Sum, 反向 trace 树)
  ↓ MLP
  ↓ 三个 head：
        - logit_bin   (det: normal / abnormal)
        - logits_c3   (c3: node/service/pod 三大类)
        - logits_type (type: 细类故障)
```

`host_state_dim` 固定为 24（6 metric × 4 dim），不足/超出会做 pad/truncate fallback。

### 6.4 训练（`train_tc_svnd.py`）

- 损失：`0.1 * BCE(bin) + 0.2 * CE(c3) + 0.7 * CE(type)`（细类优先）
- `--type_min_support 200`：训练前筛掉支持数 < 200 的细类
- 早停：监控 val loss
- ckpt 包含：`state_dict + stats + args + type_names + keep_types`

### 6.5 测试（`test_tc_svnd.py`）

- 从 ckpt 读 stats / keep_types 复用
- 支持 `--limit N` 物理切片
- 有 `hgc → h_host` 的 state_dict key 兼容映射（model 重构后的遗留）

#### 🔴 0 级（指标 4 冲到任务书 ≥85%/≥80% 的两个硬攻坚，优先做）

> 这两件事直接关系结题验收能否通过任务书指标。详细诊断见 `dataset/rca/processed/reports/eval_report_20260528_174842.md` 和 `epoch_metrics.csv`。

**0.1 预警 F1：80.28% → ≥85%**（差 4.7pp）
- **根因**：Precision=93.1% 已饱和，瓶颈在 Recall=70.7%；模型欠训练（训练曲线显示直到 epoch 4 才真正收敛，但 ckpt 仅训 5 个 epoch 就停了）+ 阈值 mad_threshold 对长尾分布偏保守。
- **建议步骤**（按 ROI 由高到低）：
  1. **零成本：多训 30~50 epoch + lr warmup + early stopping**
     - 改 `TraTopoRca/tracegnn/models/gtrace/mymodel_train.py`：把 epoch 上限拉到 50，前 3 epoch 用 1e-4 lr，之后 1e-3。
     - 预期：F1 → 84~86%（不动算法，只靠多训）。
  2. **阈值自适应（EVT 或 GMM）**
     - 当前评测脚本里 `threshold = median + k·MAD`，改成对正常 trace 异常分数尾部做 GPD 拟合（`scipy.stats.genpareto`）取 99 分位。
     - 预期：在 1 的基础上 F1 再升 2~3pp，**破 85%**。
  3. **数据增强（兜底方案）**
     - 用 `dataprocess.scripts.fault_data_fetch` 扩大故障注入样本量，特别是当前漏报多的故障类型。

**0.2 混合定位 Top-5：72.67% → ≥80%**（差 7.3pp）
- **根因**：host 异常分数（~3.0）和 svc 异常分数（~1.0）尺度不对齐，混合排序时 host 永远排前列、svc 几乎被压出 Top-5。证据：`mixed_svc_top1 = 0.000`、`mixed_svc_top5 = 0.858`（svc 完全靠 Top-5 边缘上榜）；而单独评测的 host Top-5=100%，进入混合后掉到 64%。
- **建议步骤**（按工程量由小到大）：
  1. **零成本验证（半小时）**：评测时把 host_scores 和 svc_scores 各做 z-score 归一再合并排序——只改后处理代码，不动训练。
     ```python
     host_norm = (host_scores - host_scores.mean()) / host_scores.std()
     svc_norm  = (svc_scores  - svc_scores.mean())  / svc_scores.std()
     mixed_ranked = sorted(host_norm + svc_norm, descending=True)
     ```
     位置：`TraTopoRca/tracegnn/models/gtrace/mymodel_test.py` 的 mixed 排序段；改完后跑一次 `mymodel_test --mode rca` 看新数字。
     - 预期：Mixed Top-5 → 80~84%，**可能直接达标**。
  2. **如果 z-score 不够**：分位数对齐（quantile mapping）。
  3. **如果还不够**：训练侧加 contrastive loss 强制两个分数分布同尺度。

## 12. 关键坑位提示

1. **`fault_data_fetch.py` 不过滤 StatusCode**，正常数据脚本会过滤（`StatusCode > 1` 丢弃）。两份数据特征分布不完全可比。
2. **`split_by_problem_id` 的"内部时间切分"是隐性切法**——目前赛西认证用的就是这个，结题时若要对齐其他板块再考虑改。
3. **pod 故障被跳过**——测试集里有 pod case 直接计入失败（赛西未测 pod 是因为指标 3.2/3.4 都是"应用层"，不要求 pod）。
4. **`num_features=29` 写死在 `tracegnn/models/gtrace/config.py`**，改 metric 数量时需要同步改。
5. **`host_state_dim=24` 写死在 `model_svnd.py`**，padding/truncate fallback 会静默掩盖维度错误。
6. **`test_tc_svnd.py` 有 `hgc → h_host` 的 state_dict 兼容映射**，未来重构如果改回去要删掉。
7. **trace_topo 与 trace 两份 dataprocess 脚本几乎重复**，迁移/改 bug 时容易漏改一边。
8. **CMS metric_set SPL 模板**来自可视化界面手动拷贝，metric 列名变更需要同步脚本。
9. **轨迹 CSV 实际 16 列 CamelCase**，检测报告写的是 snake_case 简化版——内部有适配层但师弟改 schema 时务必双向验证。
10. **MCP 封装代码不在本仓库**——在独立仓库 https://github.com/OraingeWZC/Trace_mcp 进行，由 wzc 维护。师弟接手 MCP 时直接 clone 那个仓库，不要在本仓库找。
